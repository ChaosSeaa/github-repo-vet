# github-repo-vet

> 在把任何 GitHub 仓库当作数据源或代码源之前，先确认它不是空壳。

一个用于 AI 编程助手（WorkBuddy / Claude Code 等）的 skill，外加一个可独立运行的命令行脚本。它解决一个很具体的问题：**你拿到的仓库地址，可能根本没有内容。**

## 它解决什么问题

开源生态里存在一类占位仓库：名字和知名项目一样，描述抄得很漂亮，但仓库里只有一个与仓库同名的空文件。它们靠蹭搜索排名、蹭视频教程的演示地址来获得访问和 star。

更麻烦的是配合 AI 使用时的场景。当有人给出「把这个仓库部署起来」这类提示词，而地址指向一个空壳时，模型有两种反应：

1. 报告仓库是空的 —— 正确，但需要模型先做了验证；
2. 用自己对同名知名项目的记忆，生成一个看起来完全正确的页面 —— **危险**。

第二种情况用户几乎无法察觉：页面能跑、结构合理、数据像样，只是来源不是那个仓库。这个 skill 的作用就是把这种情况挡在交付之前。

## 检查什么

| 信号 | 可疑阈值 | 含义 |
|---|---|---|
| `size` | 0–1 KB | 无实质内容 |
| 提交数 | 1 次，message 形如 `Create X` | 占位式建仓 |
| 根目录 | 只有一个与仓库同名的文件 | 占位惯用手法 |
| README | 不存在 | 真实项目几乎必有 |
| 描述 | 本地化、写得满，但仓库无内容 | 描述系转述知名项目 |
| 账号年龄 | < 90 天 | 批量建仓的常见特征 |
| 账号仓库 | > 10 个且多数 `size` 为 0 | 批量占位 |
| 同名项目 | 存在 star 高得多的同名仓库 | 蹭名 |

任何单一信号都不足以定罪——小项目也可能提交少。脚本按权重累加，多信号命中才给出「空壳」结论。

## 安装

作为 skill 使用（支持 SKILL.md 约定的助手会自动加载）：

```bash
git clone https://github.com/ChaosSeaa/github-repo-vet.git
cp -r github-repo-vet ~/.workbuddy/skills/
```

其他目录按各助手的 skill 约定放置即可。`SKILL.md` 的 `description` 已经写好了触发条件：部署、克隆、预览、分析或引用某个 GitHub 仓库时启用。

只想用命令的话，不需要安装，直接跑脚本：

```bash
python scripts/repo_vet.py OWNER/REPO
```

无第三方依赖，Python 3.8+ 即可。

## 使用

```bash
# 传 owner/repo
python scripts/repo_vet.py public-apis/public-apis

# 也可以直接粘贴 URL
python scripts/repo_vet.py https://github.com/chalk/chalk

# 机器可读输出
python scripts/repo_vet.py OWNER/REPO --json

# 跳过同名仓库检索（少一次 API 调用）
python scripts/repo_vet.py OWNER/REPO --no-search
```

GitHub 未认证 API 限速为每小时 60 次，单次运行消耗约 6–8 次。

## 输出示例

一个占位仓库的判定结果：

```
仓库：某账号/Public-apis
────────────────────────────────────────────────────
描述        一个集体的免费 API 列表
体积        0 KB           ⚠
提交数      1              ⚠
根目录      1 项            Public-apis
README      无              ⚠
Star/Fork   0 / 0
是否 fork   否
账号年龄    22 天
账号仓库    26 个（96% 为空）
同名最高    public-apis/public-apis  495051 star
────────────────────────────────────────────────────
可疑信号：
  ⚠ 体积 0 KB，无实质内容
  ⚠ 仅 1 次提交，占位式建仓
  ⚠ 根目录没有 README
  ⚠ 根目录仅一个占位文件：Public-apis
  ⚠ 账号注册仅 22 天
  ⚠ 账号 26 个仓库中 96% 为空
  ⚠ 同名官方仓库 public-apis/public-apis 有 495051 star，本仓库仅 0
────────────────────────────────────────────────────
结论：空壳或占位（评分 16）

建议：先向用户说明该仓库的实际状态，再决定是否改用官方源。
      同名官方候选：https://github.com/public-apis/public-apis
      不要用模型对同名项目的记忆去填充内容。
```

正常项目则为：

```
仓库：public-apis/public-apis
体积        14.1 MB        ✓
提交数      6514
根目录      7 项
README      有
Star/Fork   495051 / 55242
账号年龄    2715 天
结论：真实项目（评分 0）
```

退出码：`0` 正常，`1` 请求失败或不存在，`2` 参数错误，`3` 判定可疑或空壳。可直接嵌进 CI 或 pre-flight 检查。

## 判定规则

| 评分 | 结论 |
|---|---|
| ≥ 7 | 空壳或占位 |
| 4–6 | 可疑 |
| 1–3 | 基本正常 |
| 0 | 真实项目 |

权重：体积 ≤1 KB 记 3 分、仅 1 次提交记 2 分、无 README 记 2 分、根目录仅一个同名占位文件记 3 分、账号 < 90 天记 1 分、账号内 >70% 仓库为空记 2 分、存在 star 高得多（>50 倍）的同名仓库记 3 分。

## 设计原则

`SKILL.md` 里有一条比检查清单更重要的约束：

> 数据源为空时如实报告，不得用模型对同名项目的先验记忆补全。

清单防的是「没查」，这条防的是「查了但偷偷补全」。后者更难发现——它产出的结果看起来完全正常，用户没有任何理由怀疑。所以 skill 明确列了禁止事项，其中一条是「不做静默替换」：发现空壳后不能悄悄换成官方仓库再假装原任务完成，必须先把问题说出来。

## 已知局限

- 只覆盖公开仓库的形态特征，无法判断代码质量或项目活跃度。
- 对「个人小工具 + 新建账号 + 单次提交」这类正常但冷清的仓库，可能给出「可疑」，需要人工复核。
- GitHub 的 `size` 字段对新仓库有延迟。脚本已用「根目录是否有 README + 3 项以上文件」做交叉验证来抵消这一点，但刚创建数分钟内的仓库仍可能被低估。
- 同名检索走 GitHub Search API，速率限制比常规接口更严。
